# English-study 上游补回边界清单

## 目的

这份清单用于给 `906cae514`（`fix: restore english-study runtime baseline`）补回的大量上游文件做第一轮边界分桶，避免后续 closeout 继续被“哪些文件只是为跑起来临时补回、哪些属于 English-study 应长期保留”反复打断。

本清单当前是第一版目录级判断，不是最终逐文件裁剪结果。

## 目录级分桶

### A. 必须保留或优先保留

这些目录和文件直接参与当前仓库的启动、迁移、核心页面加载或当前已经做过的界面收口，默认优先保留：

- `label_studio/core/settings/`
- `label_studio/core/migrations/`
- `label_studio/core/management/`
- `label_studio/templates/`
- `web/dist/apps/labelstudio/`
- `web/dist/libs/editor/`
- `web/dist/libs/datamanager/`
- `web/apps/labelstudio/src/app/`
- `web/libs/editor/src/components/App/App.jsx`
- `web/libs/datamanager/src/components/App/App.jsx`
- `web/libs/datamanager/src/utils/feature-flags.js`
- `label_studio/core/static/` 中当前页面实际引用的 CSS、JS、字体、图标、图片
- `label_studio/annotation_templates/` 中当前 API 会直接暴露的模板目录与分组文件

理由：

- 这些内容直接影响 `manage.py check`、迁移、页面加载、错误页展示和当前已经完成的 UI 汉化结果
- 本轮实际修复和交付验证已经落在这些路径上
- `pyproject.toml` 已把 `web/dist/libs/datamanager/**/*`、`web/dist/libs/editor/**/*`、`web/dist/apps/labelstudio/**/*` 列为打包包含项，而 `label_studio/core/settings/base.py` 也直接把 `EDITOR_ROOT`、`DM_ROOT`、`REACT_APP_ROOT` 指向这些 `web/dist` 目录，所以它们在当前形态下属于运行时必需资产，不是单纯源码备份
- 与此同时，`web/apps/labelstudio/src/app/` 以及 `web/libs/*/src/...` 仍然要保留，因为这轮 English-study 的源码级修复、source-map 恢复和可见文案汉化就是从这些源文件完成的；如果以后要重建前端或继续做中文化，不能只留 dist 不留 src
- `label_studio/projects/api.py` 当前会直接通过 `find_dir('annotation_templates')` 扫描 `annotation_templates/**/*.yml`，并通过 `groups.txt` 组织模板分组，因此 `annotation_templates/` 不是纯历史资料，而是现有模板选择接口的一部分

### A.1 `templates/` 与 `web/` 的当前角色

- `label_studio/templates/base.html`、`simple.html`、`standard_form.html` 属于当前服务端页面骨架，必须和运行中的前端静态资源一起保留
- `label_studio/templates/401.html`、`403.html`、`404.html`、`500.html`、`log_files.html` 已在这轮完成中文收口，属于当前交付体验的一部分
- `web/dist/...` 是当前运行时直接消费的前端产物；它们不是“有源码就能先删掉”的纯备份目录
- `web/apps/.../src` 与 `web/libs/.../src` 是当前可维护的源码入口；English-study 后续若继续做文案、逻辑或构建修复，默认仍应保留

### A.2 `core/static/` 的当前分层

- 当前页面壳和账号页已经明确直接引用了一批基础静态资源：`css/uikit.css`、`css/main.css`、`css/error.css`、`css/login.css`、`css/users.css`、`css/fonts.hellix.css`、`css/Toast.min.css`、`js/jquery.min.js`、`js/helpers.js`、`js/Toast.min.js`、`images/favicon.ico`、`images/opossum_broken.svg`、`images/opossum_hanging.svg`、`images/slack.png`、`images/heidi.png`、`images/human_signal_logo.svg`、`icons/logo-black.svg`、`drf-yasg/redoc/redoc-logo.png`；这批文件应归入“当前运行时必需或高概率必需”
- `label_studio/templates/base.html` 和 `simple.html` 还会直接加载 `/react-app/main.css`、`/label-studio-frontend/main.css`、`/dm/main.css`，这进一步说明模板壳、`web/dist` 与 `core/static` 是一套同时生效的运行时组合，不适合拆开误判
- `label_studio/annotation_templates/` 中大量 `config.yml` 会引用 `/static/templates/*.png` 和 `/static/samples/*`；这批静态文件更接近“模板库/示例数据配套资源”，应和页面壳资源分开判断
- 因此，`label_studio/core/static/` 当前至少要拆成两层：一层是页面壳/登录/错误页/API 文档等直接引用资源，另一层是模板库与示例资源；前者默认保留，后者进入场景化复审
- 进一步细看后，`core/static/templates/` 里绝大多数 PNG 会被 `annotation_templates/*.yml` 的 `image:` 字段直接使用，因此它更接近“模板列表封面资源”；当前只剩 `evaluate-rag-automated-metrics.png`、`evaluate-rag-human-feedback.png`、`repeater-tag-multi-page-document-annotation.png`、`response-grading.png`、`response-moderation.png`、`side-by-side-comparison.png` 这 6 个文件暂未在现有模板 YAML 中命中，而且在排除 `static_build/staticfiles.json` 后也没有查到其他源码/文档活引用，所以目前更像未接入当前模板链路的上游封面残留
- `core/static/samples/` 则至少分成三类：被模板 YAML 或 `data_examples.json` 直接引用的 `game.wav`、`hypertext.html`、`opossum_snow.mp4`、`sample.jpg`、`sample.pdf`、`trees_in_snow.jpg`、`chairs/*`；被 `/samples/paragraphs.json` 与 `/samples/time-series.csv` 这类后端示例接口间接依赖的 `paragraphs.json` 与时间序列样例链；以及目前只在 API 示例/测试里露出的 `kittens*.jpg`、`sample.mp3` 等更偏演示资源
- 对 `sample-task-sin-headless.csv` 的追查已经完成：当前工作树没有该文件，仓库历史里也从未出现过它，而同样的悬空引用同时存在于仓库内和 `.venv` 里的 `label_studio_sdk/label_interface/data_examples.json`；因此它更像上游示例定义里的死引用，不应再被当作 English-study 当前交付缺件

### A.3 `annotation_templates/` 与 `core/examples/` 的区别

- `label_studio/annotation_templates/` 目前应先按“运行时耦合目录”处理，而不是直接降级成纯示例资料，因为 `TemplateListAPI` 会直接扫描其中的 `*.yml` 和 `groups.txt` 生成模板列表
- 这意味着 `annotation_templates/` 至少在当前 Label Studio/English-study 项目创建与模板选择链路里有接口级作用；后续若要裁剪，也应先评估是否同时要改 API、模板入口或产品流程
- 相比之下，`label_studio/core/examples/` 目前还没有查到同等级的后端目录扫描入口；它更像上游配置示例集合，仍可放在“待后置审视”队列

### B. 待确认保留

这些内容大概率来自官方 Label Studio 上游，当前能帮助仓库恢复完整性，但不一定都该作为 English-study 的长期产品资产保留：

- `label_studio/core/(other)` 里的大量通用后端文件
- `label_studio/(other)` 下的通用模块和说明文件
- `label_studio/core/static/` 中未被模板、账号页、API 文档页直接引用，且也未被当前 English-study 场景证明需要的第三方静态资源
- `label_studio/core/static/templates/` 中当前尚未被 `annotation_templates/*.yml` 命中的少数封面图（目前识别到 6 个）
- `label_studio/core/static/samples/` 中当前只在 API 示例、测试或上游示例定义里出现的样例资源，如 `kittens*.jpg`、`sample.mp3`，以及已确认属于上游死引用的 `sample-task-sin-headless.csv`

建议：

- 下一轮按“运行时必需 / 当前产品真在用 / 只是上游完整性补位”继续细分
- 优先从页面请求路径、Django 模板引用、运行时 import 链倒推，而不是直接按文件名猜

### C. 更像上游示例或可后置处理资产

这些目录更像“上游自带模板、示例、演示资源”，对当前 English-study 能跑起来未必是硬依赖，默认可以列入后置审视队列：

- `label_studio/core/examples/`（约 51 个文件）
- `label_studio/core/static/templates/` 里当前未被模板 YAML 命中的少量封面图
- `label_studio/core/static/samples/` 里当前只服务于测试、文档示例或已确认属于上游示例残留的样例文件

理由：

- 这些文件主要是官方示例配置、模板封面补充图和演示样例资源
- 它们有参考价值，但目前还没有被查到和 `annotation_templates/` 同等级的运行时扫描入口，或者只在测试/API 示例层出现
- 不适合在当前 closeout 阶段继续和运行修复文件混在一起处理

## 文档角色结论（当前版）

- `README.md`：保留，作为当前精简仓库的诚实入口说明
- `用户指南.md`：保留，作为仓库内中文操作说明，但应使用 English-study 口径，而不是再把整个仓库表述成完整上游 Label Studio 产品
- `roadmap.md`：不纳入当前交付契约；它更适合作为上游历史/背景材料，保持未跟踪或单独归档都可以，但不应被 English-study 交付文档引用为本地承诺

## 当前明确不建议再纳入 English-study 交付范围的内容

以下内容已经在本轮被明确降噪或排除，不建议再次混回 closeout 主线：

- `label_studio/core/static_build/*.js` 的机械化编译产物改动
- 根目录 `docker-compose.yml` 中的 `PLAYWRIGHT_BROWSERS_PATH` 透传，除非明确作为 OpenClaw 全局运行时配置单独保留
- `.aptlibs/`、`.playwright-browsers/`、`.venv/` 这类本地验证 workaround 目录

## 建议的下一轮细化顺序

1. 先从 `label_studio/templates/`、`web/` 和 `label_studio/core/settings/` 确认当前 English-study 明确依赖的页面和启动链
2. 再把 `label_studio/core/static/` 分成“当前页面实际引用”与“上游跟着带回但暂未证明需要”的两组
3. 最后再审 `annotation_templates/` 和 `core/examples/`，决定是整体保留、迁移到示例包，还是按 English-study 实际场景精简
